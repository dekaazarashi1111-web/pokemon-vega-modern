# Fail-fast実装方針

## 既定動作

- 生成ROMが壊れたら修復より再生成を優先する。
- 一時的な実装は許容するが、意図と撤去条件をレポートへ残す。
- 大規模な完全移植を一度に狙わず、最小の縦切りを早く動かす。
- 不明な固定アドレスは推測で確定せず、expected-byte assertionと逆アセンブル比較で測る。
- 分析に時間を使い過ぎず、検証用コードを作る。
- 可逆な仕様の曖昧さは妥当な既定値を採用してログへ残し、質問待ちにしない。
- compile失敗、赤いtest、address衝突は次の実装案を選ぶための観測結果であり、それだけでBLOCKERにしない。

## Codexが確認を求めず実行してよいこと

- feature branch/worktree作成
- 生成ディレクトリ削除
- 作業ROM再生成
- 開発依存パッケージ導入
- validator/test追加
- manifest schema拡張
- 小さなspike実装
- WIPコミット
- Git管理内と再生成領域の可逆な変更。大きな変更の直前にはcheckpoint commitを作ってよい。

物理原本 `userfile/imports/**` は変更・追跡しない。`inputs/private/**` と `inputs/reference/**` はGit管理外の安定参照/生成参照として再構築してよいが、追跡しない。

## 停止条件

次のいずれかだけをBLOCKERにする。

1. 必須の私有入力が存在しない。
2. 入力hashが期待値と異なり、代替入力がない。
3. upstream sourceが取得不能で、提供アーカイブもない。
4. toolchainの導入権限がなく、代替ビルド環境も作れない。
5. 仕様が二者択一で、後から互換に戻せず、ユーザーの意図を推定できない。

コードがコンパイルしない、ROMが起動しない、テストが赤い、アドレスが衝突した、という事実だけでは停止しない。
