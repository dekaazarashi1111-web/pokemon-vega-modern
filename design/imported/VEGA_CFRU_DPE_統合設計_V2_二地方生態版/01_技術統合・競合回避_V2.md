# 01 技術統合・競合回避 V2

## V2で追加された技術要件

### 1. カントーは「復元」ではなく新規マップ群として挿入

ベガROM内の元FRマップ番号へ原作データを上書きしてはいけない。ベガが同じマップID、スクリプトID、ワープ、フラグ、タイルセットを別用途で使用している可能性があるため、クリーンBPRJ Rev.0から抽出したカントー資産を次のように扱う。

```text
原作FRマップ資産
  ├─ blockdata / border / connections
  ├─ object events / warp coordinates
  ├─ tileset references
  └─ visual scripts
          ↓
統合版の新規マップグループ KANTO_POSTGAME
          ↓
新規マップヘッダ・新規イベントスクリプト・専用フラグへ再参照
```

再利用するのは地形、NPC座標、ジム仕掛け、建物構造であり、原作のストーリーフラグとトレーナーIDは再利用しない。

### 2. 野生出現は二つの実装方式を使い分ける

#### トーホク

```c
if (IsImportedEcologyUnlocked(map))
{
    if (RollOverlayRate(map, storyStage))
        species = ChooseImportedEcology(map, time, method, rotation);
    else
        species = ChooseOriginalVegaEncounter(map);
}
else
{
    species = ChooseOriginalVegaEncounter(map);
}
```

既存表をリポイントして新種を直接書き込む方式は採らない。これによりベガの1%枠、固有種、攻略上の入手順を保護する。

#### カントー

カントーは新規マップ群なので、12枠陸上表、5枠水上表、10枠釣り表を新規作成できる。ただし原作らしさを保つため、各通常マップで原作系統を最低4枠、比率35～60%残す。

### 3. 地方間で共有するデータ

| データ | 共有方法 |
|---|---|
| 捕獲・見つけた図鑑 | 全国図鑑フラグを共通使用 |
| 伝説捕獲済み | `FLAG_SPECIAL_xxxx_CAUGHT`を地方共通 |
| 大量発生 | 地方ごとに現在地を持つが更新カウンタは共通 |
| 研究ランク | ヒイラギ・オーキド両研究所で同じ値を参照 |
| カントー認定章 | ベガバッジとは別の8フラグ |
| 固定戦再戦受付 | シオンの救済NPCとヒイラギ研究所から同じ再戦キューを参照 |
| 進化素材製造 | BP・研究ポイント残高を共通使用 |

### 4. 最低限必要な専用領域

- カントー47地点分のマップヘッダ、イベント、ワープ、接続
- トーホク追加抽選テーブル49地点
- カントー野生テーブル47地点
- 541系統×2地方の配置参照
- 34イベント分のフラグ・変数・スクリプト
- カントー認定章8フラグ
- 伝説等125種の捕獲済み共有フラグ
- NPC再利用26件、重要アイテム置換24件
- ジム・再戦96体分のトレーナーデータ

## 前版から継承する競合分析


## 1. 単純な二重適用を禁止する理由

ファクトリーUPSはクリーンな日本語版ファイアレッドを前提に、元ROM内へフックとポインタを書き、32 MiB拡張領域へCFRU/DPEのコード・表・画像・鳴き声を置く。一方ベガIPSは同じ土台のコード、データ表、マップ、スクリプト、種族領域を独自に変更している。

解析結果は次のとおり。

| 項目 | 値 |
|---|---:|
| ファクトリーUPS元サイズ | 16,777,216 bytes |
| ファクトリーUPS先サイズ | 33,554,432 bytes |
| UPSセグメント数 | 664,194 |
| UPS XOR非ゼロ総量 | 14,680,526 bytes |
| 拡張16 MiB側の非ゼロ量 | 14,667,339 bytes |
| ベガIPSレコード数 | 20,195 |
| ベガIPS書込量 | 3,782,136 bytes |
| 先頭16 MiBの直接重複 | 775 bytes／269区間 |
| 最大連続重複 | 36 bytes |

`IPS→UPS`、`UPS→IPS`のどちらも、後から当てたパッチが先のフックやデータ表を部分的に壊す。したがって「パッチ結合」ではなく、**ベガをベースにDPE/CFRUのソースを再ビルドする移植**として扱う。

## 2. 正しいビルド順

1. クリーンなBPRJ Rev.0へベガIPSを適用し、ベガ作業ROMを作る。
2. 作業ROMを32 MiBへ拡張する。`0x01000000`以降は一旦`0xFF`またはビルドツールの想定値で初期化する。
3. ベガの種族、技、道具、特性、グラフィック、鳴き声、図鑑、野生、トレーナー、スクリプト、フラグ、SaveBlockを抽出する。
4. DPE-JPを先に移植し、DPEの全表を「ベガ既存IDを先頭に保持する構造」へ変更する。
5. CFRU-JPを後から移植し、全フックをベガROMの実アドレスへ再解決する。
6. ベガの既存イベントとトレーナーを新エンジンへ接続する互換層を入れる。
7. 外来生態、ショップ、イベント、ギミックを追加する。
8. 最終的にクリーンBPRJ Rev.0を対象とするBPS/UPSを生成する。

DPE-JPのREADMEも、DPE適用後にCFRU-JPを適用する前提を明記している。ただし、既改造ROMであるベガへそのまま`make.py`を実行してよいという意味ではない。`bytereplacement`、`hooks.s`、`repointall`、SaveBlock参照を個別監査する。

## 3. 種族ID設計

### 禁止事項

- 全国図鑑No.を内部種族IDとしてそのまま使う
- DPEの`SPECIES_BULBASAUR=1`等をベガへ上書きする
- 同じ公式ポケモンを「ベガ版」と「DPE版」の2種族に分ける
- ベガ固有種をDPEの公式種で置換する

### 採用構造

```text
InternalSpeciesId (16bit)
├─ VEGA_NATIVE_xxx      ベガ既存の公式種205
├─ VEGA_FAKEMON_xxx     ベガ／AS系オリジナル181
├─ NATIONAL_EXT_xxxx    ベガ未収録の公式種820
└─ FORM_EXT_xxxx        種族IDが必要な恒常・戦闘フォーム

NationalDexNo (0..1025)
TohokuDexNo   (0..386)
FormId        (別テーブル)
```

既存ベガ内部IDはROMから抽出するまで数値を確定しない。`data/ベガ既存図鑑ID保護台帳_386種.csv`のシンボルを先にコードへ導入し、数値の直書きを減らす。

### DPE公開基準のID容量と再配置

調査時点で固定したDPE-JP公開基準では、通常種・フォーム・内部補助種を含む定義が `SPECIES_PECHARUNT=0x59F`、`NUM_SPECIES=0x5A0` まで伸びている。ただし、この数値並びをベガへそのまま持ち込まない。ベガ既存386枠を固定したうえで、未収録公式820種、独立IDが必要な能力差フォーム、CFRU/DPE内部補助IDの順に再採番する。

- 全国図鑑1025種と内部種族ID総数は一致しない。
- 外見差だけのフォームは基礎種ID＋`FormId`とし、種族IDを浪費しない。
- `SPECIES_SHADOW_WARRIOR`等の補助IDは図鑑、野生、育て屋、PC検索から除外する。
- DPE元IDと統合後IDは `templates/species_id_map.csv` で双方向に追跡する。

## 4. テーブル統合

各データは、単純コピーではなく次の手順で再構築する。

| 対象 | 正本 | 統合方法 |
|---|---|---|
| 種族基本値 | ベガ既存＋DPE | 既存386枠を抽出して先頭保持、未収録公式種を追記 |
| グラフィック／パレット | ベガ＋DPE | 既存ポインタを保持、DPE画像を拡張領域へ再配置 |
| 鳴き声 | ベガ＋DPE | 既存サンプルを保持し、追加分のみ挿入 |
| 技・特性・道具 | ベガ＋CFRU | 既存IDの効果を互換層で保持し、新規IDを後段追加 |
| 進化 | 統合CSV | 全553条件を一括生成し、通信等に救済を設定 |
| 図鑑 | 二層 | トーホク386＋全国研究1025＋フォームタブ |
| TM／教え技 | ベガ既存番号＋CFRU拡張 | 番号ごとの互換表を作り、既存入手イベントを維持 |

## 5. フック監査

CFRU/DPEの全パッチ点を、以下の四分類でCSV化してから移植する。

1. **安全な純粋フック**：元命令列がベガでも一致し、処理だけ拡張領域へ飛ばす。
2. **要ラッパー**：ベガが同じ関数を改変している。両方の処理を呼ぶラッパーを新設。
3. **再実装**：ベガ固有の関数へCFRUロジックを手作業で統合。
4. **無効化**：追従や着せ替え等、初期版で採用しない機能のフック。

各フックは、元アドレス、期待バイト列、ベガ実バイト列、上書き長、復帰先、使用レジスタ、破壊フラグ、関連SaveBlockを記録する。期待バイト列が一致しないフックを自動適用してはいけない。

## 6. 32 MiB領域とリンク

ファクトリーUPSは拡張側に約13.99 MiBの非ゼロデータを持つため、残容量は大きくない。既存ファクトリーの後半16 MiBをそのままコピーする方式は採用しない。ベガとDPEの重複公式種205体の画像・鳴き声・表を一つにまとめ、重複資産を削減してリンクし直す。

推奨ルール:

- コードと読み取り専用表はリンカスクリプトで自動配置
- 画像・鳴き声・アニメは重複排除ハッシュを通す
- 末尾に64 KiB以上のビルド情報・将来拡張予約を残す
- `offsets.ini`とmapファイルを必ずリリースへ同梱
- ROMポインタは`0x08000000 + file_offset`を一元マクロ化

## 7. SaveBlock

1025種の見た／捕まえた、DexNav検索レベル、フォーム、研究ランク、進化カウンタ、レイド状態、拡張PCを追加するため、SaveBlockの再設計が必要。

- ベガ既存フラグ・変数・所持品・図鑑・PCの配置を先に解析
- CFRU既定のSaveBlockアドレスをそのまま使用しない
- セーブに構造バージョンとCRCを付ける
- v1.0は**新規ゲーム必須**を標準とする
- 旧ベガセーブ移行は別ツールで、主人公・手持ち・PC・進行フラグの限定変換とする
- セーブ読込失敗時に初期化せず、エラー画面とバックアップ復元を出す

## 8. テキスト・日本語UI

- 4桁図鑑番号、HP4桁、長い特性・道具名、6文字以上のポケモン名を全画面で検証
- ベガ固有名を短縮しない
- 同名公式種は一つの文字列IDに集約
- フォーム名は図鑑詳細だけで表示し、戦闘名欄を溢れさせない
- 改行制御、全角記号、性別記号、濁点、長音の幅を画面別に試験
